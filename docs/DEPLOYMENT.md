## Production Safety Boundaries

The current authoritative Production state is recorded in `docs/PROJECT_STATE_HANDOFF.md`.

- Pushes to `main` can auto-deploy Production.
- `staging` is the validation branch.
- Production DB access is exceptional, not routine.
- Production DB writes, migrations, seed, env changes, WAF changes, deploys, rollbacks, and promotions require explicit operator authorization.
- Never run demo seed in Production.
- Do not commit untracked operator/helper files unless explicitly approved.
- Do not force push to `main` or `staging`.
- Production env and WAF changes require an explicit release procedure and post-change verification.

## 3. Migration

### How Migrations Work

Antigravity HRMS uses **Prisma Migrate** for schema version control.

- Migration files live in `prisma/migrations/`
- Each migration is a `.sql` file auto-generated by Prisma
- Prisma Migrate uses migration history to apply pending migrations. Applying pending migration SQL is a database write and requires explicit target verification and authorization; idempotence is not an approval or safety guarantee.

### Development: Create a New Migration

```bash
# After editing prisma/schema.prisma:
npm run db:migrate:dev -- --name describe_your_change

# Example:
npm run db:migrate:dev -- --name add_employee_emergency_contact
```

### Production: Apply Pending Migrations

In self-hosted Docker Compose, schema migration is separate from application runner startup and is executed by the builder-based migrate service or a separately authorized operator CLI invocation. Full-stack up may automatically start the migration job and therefore requires explicit authorization for its database mutations. Neither path automatically verifies Human Owner approval, database identity or release-image freshness.

```bash
# Via Docker Compose (canonical release owner — migrate runs before app starts)
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# Explicit operator script (deliberate operator path — requires separate Human Owner authorization)
DATABASE_URL="postgresql://..." npm run db:migrate:prod
```

### Check Migration Status

```bash
# Read-only DB query; separate approval required. Use a reviewed builder image, an existing healthy DB and a verified target.
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm --no-deps migrate npx prisma migrate status
```

### Reset All Migrations (⚠️ DESTRUCTIVE — dev only)

```bash
# Drops entire DB and re-runs all migrations + seed
npm run db:reset
```

## 4. Seed & Bootstrap

> [!IMPORTANT]
> **Single Seed Governance Invariant:** Application runner startup **NEVER** invokes seed scripts or administrator bootstrap procedures. Application runner replicas execute zero seed scripts. Seed scripts and administrator bootstrap are separate operator workflows and require separate Human Owner authorization for Production. Applying pending migrations is a separate database-write path: migration SQL may INSERT, UPDATE or backfill data, including initialization, without a seed-script invocation. Full-stack Compose may start the dedicated migrate service; this is not migration or seed execution by the application runner.

### Database Seeding Overview

The seed script (`prisma/seed.ts`) has two modes governed by `DEMO_MODE` and `NODE_ENV`:

1. **Production System Essentials (`npm run db:seed:prod`)**:
   - Initialized when `NODE_ENV=production` or `DEMO_MODE=false`.
   - Initializes only canonical RBAC system roles: `admin`, `hr`, `manager`, `employee`.
   - Creates **zero** default users, **zero** demo credentials, and **zero** tenant organizations.
   - Platform administration provisioning is a separate, explicitly controlled procedure.

2. **Development / Sandbox Demo Simulation (`npm run db:seed:demo`)**:
   - Active only in non-production environments when `DEMO_MODE=true`.
   - Populates sandbox fixtures (organization, branch, sample departments, positions, shifts, statutory payroll rules, and fictional test personas).
   - Demo credentials are controlled by `DEMO_USER_PASSWORD` and are intended strictly for local development and QA sandboxes.

### Running Seed (Explicit Operator Action Only)

Seed scripts are **never** invoked by application runner startup. To run a seed script as an explicit operator action:

```bash
# Local development sandbox seed (requires local DB and DEMO_MODE=true):
npm run db:seed:demo

# Production system essentials (initializes 4 RBAC roles only, requires operator authorization):
npm run db:seed:prod
```

### Fresh self-hosted database prerequisites

Before any application-start example below, verify the target and authorize each database mutation. Required initialization order is schema migration -> system essentials -> separately approved admin/bootstrap -> application startup. The production seed upserts only admin/hr/manager/employee roles; it does not provision administrator access. No generic self-hosted bootstrap command or verification criteria are defined here: STOP before application startup until an approved procedure is available. Existing initialized databases must not be reseeded or bootstrapped merely because the app restarts. A standalone runner requires a reachable, release-compatible migrated database and completed required initialization; its connectivity check does not prove these conditions.

## 5. Deploy

### Quick Start (Initialized Self-hosted Database Only)

```bash
# 1. Clone and configure
git clone https://github.com/<org>/antigravity-hrms.git && cd antigravity-hrms
cp .env.example .env && nano .env

# 2. Start full stack (DB + Redis + Migrate + App)
docker compose up -d

# 3. Check status
docker compose ps

# 4. View app logs
docker compose logs -f app
```

### Production Deploy

> [!IMPORTANT]
> For this project's Vercel Production release, do not deploy from this runbook without explicit operator approval. Validate on `staging` first, confirm `main` points to the intended release SHA, and preserve untracked helper files.

```bash
# Using production override (no exposed DB ports, resource limits, json logs)
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# Or via npm script:
npm run docker:up:prod
```

### Verify Deployment

```bash
# Check all services are healthy
docker compose ps

# Test health endpoint
curl http://localhost:3000/api/health

# Expected response (uptime and timestamp vary):
# {"success":true,"data":{"status":"HEALTHY","version":"1.0.0","uptime":123.45},"meta":{"timestamp":"<ISO-8601 timestamp>"}}
# /api/health proves application/process responsiveness only; it performs no DB query and reports no DB latency.
# HTTP 200 does not verify DB connectivity, schema readiness, migration/seed completion or administrator bootstrap completion.
```

### Self-hosted release updates

The current Compose services build images from source; they do not select registry images. Code-only updates require an explicitly authorized build and app recreation against an initialized, compatible database with no pending migrations. Schema releases require app and migrate images from the same reviewed revision, explicit migration completion and verified success before app recreation. Plain up is not proof of release freshness. The release-specific commands and target checks require separate Human Owner approval. The current single app container does not guarantee zero downtime.

### Deploying to VPS / Cloud VM

```bash
# On the server:

# Install Docker + Compose
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER

# Clone repo
git clone https://github.com/<org>/antigravity-hrms.git /opt/antigravity-hrms
cd /opt/antigravity-hrms

# Configure env
cp .env.example .env && nano .env

# Start
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# Enable restart on server reboot (already handled by restart: always)
# Optional: set up systemd service for docker compose
```

### CI/CD via GitHub Actions

Push to `main` branch triggers:

1. **CI workflow** (`ci.yml`): typecheck → lint → test → build → compose validate
2. **Docker workflow** (`docker-publish.yml`): builds multi-platform image and pushes to `ghcr.io`

The Docker workflow publishes registry images but does not wire them into the current build-only Compose services. Follow the reviewed source-build release contract above; do not use docker compose pull app with this configuration. Registry-image deployment requires a separately reviewed Compose image contract.

## 6. Rollback

### Application rollback contract

The current build-only Compose configuration does not consume IMAGE_TAG or select registry images. The former registry-tag rollback command is unsupported. STOP and obtain a separately reviewed rollback procedure; an application rollback is not a database rollback.

### Rollback Database Migration

> [!CAUTION]
> Prisma Migrate does **not** support automatic rollback.
> You must manually revert the SQL changes.

**Step 1 — Identify the bad migration:**

```bash
docker compose -f docker-compose.yml -f docker-compose.prod.yml run --rm --no-deps migrate npx prisma migrate status
```

**Step 2 — Restore from backup (safest option):**

See [Restore](#restore) section below.

**Step 3 — Manual SQL rollback (advanced):**

```bash
# Connect to PostgreSQL
docker compose exec db psql -U postgres -d antigravity_hrms

# Run the reverse SQL (e.g., DROP the column/table added in the bad migration)
ALTER TABLE "Employee" DROP COLUMN IF EXISTS "emergencyContact";

# Then remove the migration record from Prisma's tracking table
DELETE FROM "_prisma_migrations" WHERE migration_name = '20260901_add_employee_emergency_contact';
```

**Step 4 — Mark migration as rolled back:**

```bash
npx prisma migrate resolve --rolled-back 20260901_add_employee_emergency_contact
```

## 7. Backup

### Manual Backup

```bash
# Full database dump (SQL format, compressed)
docker compose exec db pg_dump \
  -U postgres \
  -d antigravity_hrms \
  --format=custom \
  --compress=9 \
  > backup_$(date +%Y%m%d_%H%M%S).dump

# Or via host (if port 5432 exposed)
pg_dump \
  "postgresql://postgres:<password>@localhost:5432/antigravity_hrms" \
  --format=custom \
  --compress=9 \
  > backup_$(date +%Y%m%d_%H%M%S).dump
```

### Automated Daily Backup Script

Create `/opt/scripts/backup-hrms.sh`:

```bash
#!/bin/bash
# Daily backup of Antigravity HRMS database
# Retention: 30 days

BACKUP_DIR="/opt/backups/antigravity-hrms"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/db_${TIMESTAMP}.dump"
RETENTION_DAYS=30

mkdir -p "$BACKUP_DIR"

# Run pg_dump inside the postgres container
docker compose -f /opt/antigravity-hrms/docker-compose.yml \
  exec -T db pg_dump \
  -U postgres \
  -d antigravity_hrms \
  --format=custom \
  --compress=9 \
  > "$BACKUP_FILE"

echo "✅ Backup created: $BACKUP_FILE ($(du -sh "$BACKUP_FILE" | cut -f1))"

# Prune old backups
find "$BACKUP_DIR" -name "*.dump" -mtime +$RETENTION_DAYS -delete
echo "🧹 Pruned backups older than ${RETENTION_DAYS} days"
```

```bash
chmod +x /opt/scripts/backup-hrms.sh

# Schedule via cron — runs daily at 02:00
crontab -e
# Add: 0 2 * * * /opt/scripts/backup-hrms.sh >> /var/log/hrms-backup.log 2>&1
```

### Backup Uploads (Avatars)

```bash
# Backup the uploads Docker volume
docker run --rm \
  -v antigravity-hrms_uploads_data:/uploads \
  -v $(pwd):/backup \
  alpine \
  tar czf /backup/uploads_$(date +%Y%m%d).tar.gz /uploads
```

## 8. Restore

### Restore Database from Backup

> [!WARNING]
> Restoring **replaces all current data**. Take a backup of current state first.

```bash
# Step 1: Stop the app (keep DB running)
docker compose stop app

# Step 2: Drop and recreate the database
docker compose exec db psql -U postgres -c "DROP DATABASE IF EXISTS antigravity_hrms;"
docker compose exec db psql -U postgres -c "CREATE DATABASE antigravity_hrms;"

# Step 3: Restore from dump file
docker compose exec -T db pg_restore \
  -U postgres \
  -d antigravity_hrms \
  --clean \
  --if-exists \
  < backup_20260901_020000.dump

# Step 4: Restart app
docker compose start app

# Step 5: Verify application/process response only
curl http://localhost:3000/api/health
# This does not verify DB restore success or data/schema integrity; separate authorized verification is required.
```

### Restore Uploads

```bash
# Restore uploads volume from tar backup
docker run --rm \
  -v antigravity-hrms_uploads_data:/uploads \
  -v $(pwd):/backup \
  alpine \
  tar xzf /backup/uploads_20260901.tar.gz -C /
```

## 9. Troubleshooting

### App Not Starting

**Symptom:** `docker compose ps` shows `app` as `unhealthy` or `restarting`

```bash
# Check app logs for startup errors
docker compose logs app --tail=100

# Common causes:
# - DATABASE_URL is wrong → fix .env, restart
# - AUTH_SECRET is < 32 chars → generate new one
# - Port 3000 already in use → change APP_PORT in .env
```

### Database Connection Error

**Symptom:** `Error: P1001 Can't reach database server`

```bash
# 1. Check DB container is running
docker compose ps db

# 2. Check DB is healthy
docker compose exec db pg_isready -U postgres

# 3. Verify DATABASE_URL in .env matches POSTGRES_* vars
# Inside compose, use: postgresql://postgres:<pass>@db:5432/antigravity_hrms
# Outside compose (local), use: postgresql://postgres:<pass>@localhost:5432/antigravity_hrms

# 4. Restart DB and app
docker compose restart db
sleep 5
docker compose restart app
```

### Migration Failed

**Symptom:** `migrate` service exits with non-zero code

```bash
# Check migrate logs
docker compose logs migrate

# Common causes:
# 1. DB not ready → increase healthcheck retries in docker-compose.yml
# 2. Migration conflict → check prisma/migrations/ for drift
# 3. Duplicate migration → check _prisma_migrations table

# Inspect migration state
docker compose exec db psql -U postgres -d antigravity_hrms \
  -c "SELECT migration_name, finished_at, applied_steps_count FROM _prisma_migrations ORDER BY started_at DESC LIMIT 10;"
```

### Redis Connection Error

**Symptom:** Cache misses, job runner errors

```bash
# Check Redis is running
docker compose ps redis

# Test Redis connectivity
docker compose exec redis redis-cli ping
# Expected: PONG

# Check Redis logs
docker compose logs redis

# App degrades gracefully without Redis (uses L1 in-memory cache only)
# To disable Redis: set REDIS_URL="" in .env
```

### Out of Memory

**Symptom:** Container killed (OOMKilled), large exports crash

```bash
# Check container memory usage
docker stats --no-stream

# Solutions:
# 1. Increase memory limit in docker-compose.prod.yml
# 2. Large reports: exports are capped at 5,000 rows (Phase 25 protection)
# 3. Add swap space on the host:
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
```

### High CPU Usage

```bash
# Identify which process is hot
docker stats

# Profile Node.js (inside container)
docker compose exec app node --prof server.js &
# ... reproduce the load ...
# kill %1 && node --prof-process isolate-*.log > profile.txt
```

### Health Check Failing

```bash
# Test health endpoint manually
curl -v http://localhost:3000/api/health

# Expected 200 response (uptime and timestamp vary):
# {
#   "success": true,
#   "data": { "status": "HEALTHY", "version": "1.0.0", "uptime": 123.45 },
#   "meta": { "timestamp": "<ISO-8601 timestamp>" }
# }

# /api/health performs no DB query and reports no DB latency.
# HTTP 200 proves application/process responsiveness, not DB connectivity, schema readiness, migration/seed completion or administrator bootstrap completion.
# If the endpoint is unreachable or does not return the documented 200 response, inspect application/container logs; DB checks require separate authorization.
```

### Reset Everything (Last Resort)

> [!CAUTION]
> This destroys ALL data. Use only in dev/staging.

```bash
# Stop all containers, remove volumes (DESTROYS ALL DATA)
docker compose down -v

# Remove built images
docker rmi antigravity-hrms

# Start fresh
docker compose up -d
```
